## O achado, por extenso

### Grupo 1 — a chamada de `autonomy_session_row` ganhou uma quebra de linha (I1 desta missão)

`mut_RUN_blocked_not_escalated` e `mut_RUN_app_down_not_escalated` (`tests/check-mutation.sh:982`
e `:1013`) ancoram um intervalo de `sed` que **começa** na linha:

```
"$( [ "$gate_rc" -eq 0 ] && echo pass || echo fail )" "$GATE_WHY"
```

casada como **fim de linha exato** (`$` do regex). O incremento I1 desta missão (`4571faf`) passou
a chamar `autonomy_session_row` com três argumentos novos (`pending_before`/`pending_after`/
`increments_total`), e para isso quebrou essa chamada em três linhas com continuação `\`
(`bin/sdd:4153-4155` hoje):

```bash
autonomy_session_row "$phase" "${attempts[$phase]}" "false" "$moved" \
  "$( [ "$gate_rc" -eq 0 ] && echo pass || echo fail )" "$GATE_WHY" \
  "$exec_before" "$exec_after" "$exec_total"
```

A linha que os dois mutantes procuram agora termina em ` \` (continuação), não em `"$GATE_WHY"`
seguido de quebra de linha — o `sed` não encontra o início do intervalo, a mutação não aplica nada,
`cmp -s` no harness detecta arquivo idêntico e devolve rc 90 (`CATALOGUE-BROKEN`). As linhas que a
substituição em si visava (`if handoff_blocked_escalation "$phase"; then return 3; fi` em
`bin/sdd:4172`, `if app_down_escalation "$phase"; then return 3; fi` em `:4176`) continuam intactas
e sem mutante — a proteção sumiu por inteiro, não degradou.

**Isto não é um achado desta missão sobre um defeito do produto** — é a própria I1 quebrando a
âncora de dois mutantes de uma missão anterior (`20260828-o-gate-sabe-que-o-app-caiu`), porque o
ritual de "provar em cópia antes do commit" que o I1 seguiu olhou só para os mutantes que o próprio
I1 tocava, nunca para os que moram no **mesmo bloco de código** por acaso.

### Grupo 2 — a cláusula `.moved != false` entrou DENTRO de `def outcome:` (achado #2 da r1 do REVIEW)

`mut_AUTONOMY_outcome_reads_moved_only`, `mut_AUTONOMY_progress_ignored` e
`mut_AUTONOMY_progress_null_blind` (`tests/check-mutation.sh:2124`, `:2278`, `:2289`) ancoram,
literalmente, o texto:

```
def outcome: if .gate == "pass" then "advanced" elif (.pending_before != null and .pending_after != null and .pending_after < .pending_before) then "advanced" elif .moved == true then "churned" else "idle" end;
```

O texto **hoje** em `bin/sdd:1925` (achado #2 da r1 do REVIEW, corrigido no commit `f00c2dc`,
"a inferência do caminho histórico creditava até a sessão que não mexeu no disco") é:

```
def outcome: if .gate == "pass" then "advanced" elif (.pending_before != null and .pending_after != null and .pending_after < .pending_before and .moved != false) then "advanced" elif .moved == true then "churned" else "idle" end;
```

A cláusula `and .moved != false` entrou **dentro** do parêntese do braço de progresso — exatamente
onde os três mutantes fazem o `sed` casar a string inteira. Nenhum bate mais: rc 90 para os três.
`f00c2dc` é um commit da **r1 do REVIEW**, que reancorou os mutantes que a PRÓPRIA rodada
introduzia (o `40-review-r1.md` cita isso: "os **15** mutantes que esta missão acrescentou ou
re-ancorou foram verificados... nenhum sai rc 90") — mas os dois mutantes de `outcome` que o **I2**
tinha reancorado ANTES da r1 (`AUTONOMY_outcome_reads_moved_only`) e os dois que o I2 introduziu
(`AUTONOMY_progress_ignored`, `AUTONOMY_progress_null_blind`) não estavam na lista de mutantes que
a r1 verificou como "desta rodada" — eram mutantes de uma rodada **anterior**, tocados de raspão
pela edição de uma rodada **posterior**, na mesma linha de código.

### O padrão comum às duas causas

Nenhuma sessão rodou o catálogo **inteiro**, de ponta a ponta, entre a última edição de código
(`99da6d8`, o `F1`) e agora — declarado como risco em `20-handoff-exec.md` § Riscos ("O catálogo
completo não foi rodado nesta fase... o `score: N caught of N` de ponta a ponta só sai do `sdd

que o mutante **que a sessão está tocando** ainda casa — nunca prova que a edição não descasou um
mutante **de outra sessão** que mora no mesmo trecho de texto. É exatamente o risco que o
`01-plano.md` já nomeava ("O mutante re-ancorado... fica no-op e o `sdd health` responde rc 90 na
fase PR"), só que ele se materializou em **cinco** mutantes por **dois** commits diferentes
(`4571faf` do I1 e `f00c2dc` da r1 do REVIEW), não apenas nos dois que o próprio plano citava por
nome.

## Por que esta sessão não conserta

Reancorar um `sed`/`perl` de mutante é escolher o **novo texto-âncora certo** e provar, numa cópia,
que a mutação (a) aplica exatamente uma mudança, (b) o arquivo mutado ainda compila (`bash -n`), e
(c) a suíte fica vermelha **na asserção nomeada pelo comentário do mutante**, nenhuma outra — é o
ritual de TDD que este próprio repositório exige de todo mutante novo (`CLAUDE.md` § "TDD aqui
dentro"). É julgamento sobre teste de produto, não montagem de artefato: cabe a uma sessão de
código (EXEC ou uma rodada extra de REVIEW), não ao `sdd-publisher`, cujo papel é mecânico por
desenho. "Do not fix it — it is not your phase" — a regra vale tanto para o produto quanto para o
próprio arnês de teste do produto.
